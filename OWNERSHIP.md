# Project Ownership And Governance

Community participation makes Nido stronger. This policy gives contributors a
clear way to propose and build improvements while keeping project stewardship
and decision-making predictable.

## Project Owner

EZ Vibes Nido was created by and is led by Evan Bonertz, founder of EZ Vibes.
Evan is the Project Owner and final decision-maker for product direction,
roadmap priority, repository administration, releases, deployments, access to
project infrastructure, and merge decisions.

The repository is public to invite useful participation. Public visibility and
acceptance of a contribution do not transfer ownership or governance of Nido or
EZ Vibes to a contributor.

## Contributions

Contributors can propose features, report problems, participate in technical
discussion, and submit pull requests. Contributors retain copyright in original
material they create unless they sign a separate written assignment, while
granting the Project Owner the broad rights described in
[CONTRIBUTOR_TERMS.md](CONTRIBUTOR_TERMS.md).

Authorship credit is valuable and preserved through the contribution history.
Participation does not, by itself, create equity, partnership rights,
employment status, administrative access, merge authority, or control over the
project.

## Feature Requests

Feature requests from users and contributors are welcome through the GitHub
feature-request template. Requests should explain the user problem, desired
outcome, and acceptance criteria before proposing a large implementation.

The Project Owner evaluates requests based on product fit, user value, safety,
maintenance cost, compatibility, and available capacity. Discussion or approval
of a request does not guarantee a release date. Contributors who want to
implement an approved request should obtain issue assignment or maintainer
confirmation before beginning substantial work.

Ideas discovered during pull-request review that are useful but outside the
accepted issue scope should normally become follow-up feature requests rather
than unannounced merge requirements.

## Review And Merge

- The Project Owner has final approval and merge authority.
- External contributors do not self-merge.
- Security, authentication, data, deployment, and infrastructure changes require
  explicit owner review.
- Review comments should identify whether they are required for the current pull
  request or proposed as a non-blocking follow-up.
- Accepted code may later be modified, reverted, relicensed, or removed under
  the rights granted to the Project Owner.
